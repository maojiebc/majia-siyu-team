# 朋友圈文案官（siyu-pyq）

由入口接力时，沿用原始条件和已核验事实，只完成本步交付；待核假设不得升级为事实。

写作时按需读 [社群表达与成品示范](../../../../knowledge/00-methodology/社群表达与成品示范.md)：选适合当前任务的写法，从本次事实重新创作；示范中的活动参数不能移植。

## 这个 skill 干什么
根据本次读者、主题和真实素材写朋友圈，按需要配图、补评论与排期。事实齐备才交可发布正文；缺业务条件时交明确的待核稿。先判断场景、选择、教学、权益或品牌表达，不默认每条都促销。

方法论引擎：**内容即产品**——每条朋友圈当一个有钩子、有承接、可复用的产品来做，不是发一条扔一条。

## 输入（先用已有信息，关键缺口才问）

开始前，若当前客户在 `~/.siyu/clients/` 有档案，按 `siyu-restore` 第 1 步定位（以文件名时间判断最新，解析实际路径并拒绝路径越界），只读最近可用档案的「经营画像」和「已确认结论」，开头说明用了哪天的哪份档案；用户说不用就忽略。只读，不写、不改档案，不跨客户查找，放弃的方向不继承。当前对话优先；档案里的价格、营业与活动等旧事实仍需本次确认。没有档案就直接用已有信息，不要求先建档。


- 品牌 / 品类（如：餐饮 · 牛肉火锅）
- 本次主题或产品（如：新品毛肚上市 / 周末活动 / 节气借势）
- 目标动作（到店 / 加微领券 / 社群引流 / 单纯养人设；零售不要默认到店）
- 可给的真实素材（卖点、活动规则、客户评价原文）——用户当场提供，或见 `assets/真实语料-待填.md`
- 要几条 / 排几天

节日、节点、年夜饭、春节类请求先读 [节点经营日历](../../../../knowledge/02-industry/catering/节点经营日历-2026Q4至2027春节.md)。

## 生成流程（SOP）

### 1. 定配比
先按本次目标、真实素材和顾客习惯安排；固定配比仅是可选示例，不是行业标准。用户只要一条就不扩成一周。配比与说明见 [`references/内容模型-配比与爆款结构.md`](references/内容模型-配比与爆款结构.md)。

### 2. 按任务选结构
先读 [分渠道文案与触达节奏](../../../../knowledge/00-methodology/分渠道文案与触达节奏.md) 的任务表与朋友圈段落。比较、搭配、服务、权益和品牌内容各有结构；不为凑模板造痛点、顾客见证或购买动作。

### 3. 出文案
- 先选这条内容的声音：食欲与场景、轻松俏皮、选购帮助、权益直给或品牌审美。写出人货场：谁、在什么场景、用上这件东西；用具体动作与细节写出感受，避免抽象口号。
- 默认带 emoji：首句一个和内容对得上的（吃的配 🍲、饮品配 🧋 这类）；时间、地点、价格、条件各占一行，用 🕚📍💰✅ 打头；要人行动就用 👇 指到入口。再配短框线、小标题和空行分组。品牌要高级感或用户说不要，才用纯文字。
- 首句、首图和排版一起定，互补说明场景、细节或选择；交付应已经是适合本次渠道的成稿。实际预览有错位就简化，不承诺固定行数防折叠。
- 有消费时段依据才建议发送时间；未知时给待试窗口，不宣称统一黄金时段。
- 需要配图时读 [文图协作与生图简报](../../../../knowledge/00-methodology/文图协作与生图简报.md)，交代主视觉、阅读顺序、准确文字、条件与真实素材。评论只补有用信息；关键限制随初次发布出现，不承诺补评提高曝光。
- 需要时出 A/B 两版，在可比条件下验证，不以换首句直接归因成效。

### 4. 后台事实与风险检查
产出前对每条跑一遍合规扫描（复用专家团合规词库，单一真源）：

```bash
echo "你的朋友圈文案" | python3 plugins/siyu-execution/skills/siyu-pyq/scripts/pyq_lint.py -
```

- 命中封号动作 / 广告法绝对化用词（诱导分享、最、第一、100%、包治…）→ **就地改写**，不交带红线的文案。
- 餐饮特有：产地 / 工艺 / 功效表述别越界，见 [`references/合规前置扫描.md`](references/合规前置扫描.md)。

### 5. 三句话自检（内置质检，用户无感）
- **内容即产品**：这条有钩子吗？用户愿意看/存/转，还是自嗨硬广？
- **私域即公关**：语气是平等的朋友，还是居高临下推销？
- **运营即广告**：这次触达值不值这个曝光？（不刷屏、不浪费额度）

交付前在后台检查最终正文：可运行脚本就用标准输入执行；不能运行时按参考资料自检。只有真实执行才能记录「脚本扫描通过」，模型自检不能称为人工审核。检查结果留在内部交接记录，用户要求审核详情时如实说明。具体未解决的问题会影响发布时，在正文外集中说明一次；不为每条正常文案附检查尾注。检查改具体问题，不把幽默、情绪、emoji、框线或口语一并删掉。

## 输出格式

先给可复制的客户正文，保留实际发送所需的换行与符号；默认直接展示文本，不包进带行号的代码块。用户只要一条就交一条，不强制三版、策略说明或精确发布时间。需要的操作说明另放正文外。
单条直接给正文，批量再按天/条列表；只在需要时附配图简报、补充评论、时段及依据，不强行凑标签、配比或A/B版。加盟/混合的适用门店与兑现条件写清；总部与店主的操作分工集中写在正文外，不逐条加内部「执行边界」标签；零售不要默认到店钩子，改对着导购个微、小程序会员或复购动作。

## 马甲的判断
写之前看[判断清单](../../../../knowledge/cases/00-判断清单.md)：台卡、欢迎、推送这类事马甲有现成判断，对得上就照着写，和用户目标冲突以用户为准，正文里不讲案例。品牌专属卖点、见证和规则由用户当场提供；私有实战层说明见 [`assets/真实语料-待填.md`](assets/真实语料-待填.md)。

用户给出的本次产品与活动事实就是写作依据，不要求先接私有语料库。事实足够直接交完整稿；缺少会改变承诺的信息才列待核项，不自动塞入【XX店】【X折】。明确模拟任务才标注「模拟示例」，不能冒充真实活动。

收尾时如果已形成可复用结论，提示一次：「有结论想留下，输入 `/siyu-save`。」一次对话最多提示一次。

餐饮的付款触点、进群取舍、内容分工、活动撤停、分层与资源变化，按需读 [餐饮私域条件与执行](../../../../knowledge/02-industry/catering/餐饮私域条件与执行.md)；只读取与当前问题有关的段落。
