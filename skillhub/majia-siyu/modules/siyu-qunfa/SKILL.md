# 社群群发官（siyu-qunfa）

由入口接力时，沿用原始条件和已核验事实，只完成本步交付；待核假设不得升级为事实。

写作时按需读 [社群表达与成品示范](../_knowledge/00-methodology/社群表达与成品示范.md)：选适合当前任务的写法，从本次事实重新创作；示范中的活动参数不能移植。

## 这个 skill 干什么
根据群的用途和本次真实信息生成通知、选择帮助、服务或活动文案。栏目是安排长期内容的工具，单条任务不扩成栏目规划；缺关键条件时交待核稿。

方法论引擎：**运营即广告**——每条群发都是一次有成本的触达，要对打开率和承接负责，不刷屏、不浪费触达额度。

> 群发长期低于自家可核实的基线时，先查群定位、预期与回复承接；没有可见的打开记录，就不下打开率结论。文案不能替代机制诊断，不用无来源的行业阈值。

## 输入（先用已有信息，关键缺口才问）

开始前，若当前客户在 `~/.siyu/clients/` 有档案，按 `siyu-restore` 第 1 步定位（以文件名时间判断最新，解析实际路径并拒绝路径越界），只读最近可用档案的「经营画像」和「已确认结论」，开头说明用了哪天的哪份档案；用户说不用就忽略。只读，不写、不改档案，不跨客户查找，放弃的方向不继承。当前对话优先；档案里的价格、营业与活动等旧事实仍需本次确认。没有档案就直接用已有信息，不要求先建档。


- 品牌/品类 + 群类型（福利群/铁粉群/新客群/门店群）
- 本次要发什么（每日栏目 / 某活动 / 某新品）
- 人设语气（实在/温暖/玩梗… 见 references）
- 目标动作（到店核销/小程序下单/接龙报名/加个人号；零售不要默认到店核销）
- 真实优惠条件（用户当场提供，避免"假大空一键转发"；说明见 `assets/真实语料-待填.md`）
- 发几个栏目 / 排几天

节日、节点、年夜饭、春节类请求先读 [节点经营日历](../_knowledge/02-industry/catering/节点经营日历-2026Q4至2027春节.md)。

## 生成流程（SOP）

### 1. 先定本群任务，需要时选栏目
默认栏目库：每日好物 / 限时秒杀 / 干货一条 / 社群专属价 / 接龙互动 / 到店提醒。
先读 [分渠道文案与触达节奏](../_knowledge/00-methodology/分渠道文案与触达节奏.md) 的渠道、时间和事实表。栏目能表达预期，效果需另证；栏目选择见 [`references/栏目模型与打开率.md`](references/栏目模型与打开率.md)。

### 2. 按本群任务组织
按任务组织：**首句说明本次信息 → 正文给事实 → 需要时给明确的下一步**；只有真实期限已确认时才写截止。催订须按节点日历的对应阶段模板保留「截至【填：核对时间】」「【填：真实余位】」和本店接单入口，填完核位才发；不能退回泛泛的意向登记。
首句说清和本群有什么关系。

### 3. 出文案 + 人设语气
- 像群主在张罗一件具体的事：先给本群关心的场景、好物或安排，再接必要条件。默认带 emoji：首句一个点题的，时间、地点、价格、条件各占一行、用 emoji 打头，要人行动就用 👇；再用短标题、分组和空行形成栏目识别。品牌或用户说不要才用纯文字。
- 商品、选项和对应条件分组对齐；长短服从任务。特殊字符在发送界面难读或错位就简化，价格、日期与入口保持易复制。
- 互动给一个值得回答的选择，并准备接话；没有互动目的就直接通知。卡片标题与正文各司其职。
- 按人设出对应语气版；需要时出 A/B（换钩子首句）。
- 排期对齐消费决策、履约与回复能力；未知时给待试窗口，不默认午间/晚间/睡前。
- 配图按 [文图协作与生图简报](../_knowledge/00-methodology/文图协作与生图简报.md)，核对本店商品与规则；总部素材先经本店确认。

### 4. 后台事实与风险检查
```bash
echo "群发文案" | python3 modules/siyu-qunfa/scripts/qunfa_lint.py -
```
除通用红线（第一/100%/绝对化），**重点扫群发特有的诱导分享**（转发得赠/集赞/拉 X 人进群）——这类是企微封号高发。命中就地改走企微官方路径。见 [`references/合规前置扫描.md`](references/合规前置扫描.md)。

### 5. 三句话自检
- **运营即广告**：这条触达值不值？会不会让人退群？
- **内容即产品**：除了促销，给了用户什么（信息/福利/参与感）？
- **私域即公关**：像群主在张罗，还是像机器人轰炸？

## 活动模板
- **平台权益联动**：先核验门店权限、权益资格及核销退款，不保证隐藏、不破价或排名。见 [`references/活动模板-偷着打折.md`](references/活动模板-偷着打折.md)。

交付前在后台检查最终正文：可运行脚本就用标准输入执行；不能运行时按参考资料自检。只有真实执行才能记录「脚本扫描通过」，模型自检不能称为人工审核。检查结果留在内部交接记录，用户要求审核详情时如实说明。具体未解决的问题会影响发布时，在正文外集中说明一次；不为每条正常文案附检查尾注。检查改具体问题，不把幽默、情绪、emoji、框线或口语一并删掉。

改写记录只说明「参与方式已改为无需分享」，不给原违规广告复述或引号示例；客户正文和操作说明都检查，避免把风险句带进交付物。

## 输出格式

先给可复制的客户正文，保留实际发送所需的换行与符号；默认直接展示文本，不包进带行号的代码块。用户只要一条就交一条，不强制三版、策略说明或精确发布时间。需要的操作说明另放正文外。
单条直接交正文；需要批量才按栏目/天组织。时段、参与动作、配图、A/B和机制提醒按任务需要提供，不给纯通知强加回复动作或群沉默诊断。加盟/混合的适用门店与兑现条件写清；总部与店主的操作分工集中写在正文外，不逐条加内部「执行边界」标签；零售不要默认到店钩子。

## 马甲的判断
写之前看[判断清单](../_knowledge/cases/00-判断清单.md)：台卡、欢迎、推送这类事马甲有现成判断，对得上就照着写，和用户目标冲突以用户为准，正文里不讲案例。真实优惠、栏目排期由用户当场提供；私有实战层说明见 [`assets/真实语料-待填.md`](assets/真实语料-待填.md)。

收尾时如果已形成可复用结论，提示一次：「有结论想留下，输入 `/siyu-save`。」一次对话最多提示一次。

门店收银、进群承接、开业、核销排错、员工激励和日常内容，按具体问题读取 [门店会员执行参考](../_knowledge/02-industry/catering/门店会员执行参考.md)；口径与算账交 majia-huiyuan。

餐饮的付款触点、进群取舍、内容分工、活动撤停、分层与资源变化，按需读 [餐饮私域条件与执行](../_knowledge/02-industry/catering/餐饮私域条件与执行.md)；只读取与当前问题有关的段落。
