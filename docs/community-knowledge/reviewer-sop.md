# 社区语料快速批阅 SOP

评审员 = 飞书「案例提交」这张表的协作者。不要改仓库里的 JSONL。机器只收集证据、写建议等级和印证数。

## 一次批一条（大约 1–2 分钟后生效）

1. 打开飞书 Base，切到「待批阅」视图（「评审结论」为空或「待审」）。
2. 看判断句、数字/证据、「印证数」、「建议等级」。建议不是命令：两家印证只说明可以认真看，不自动过。
3. 能用：把「评审结论」改成 **通过**，勾「评审等级」A / B / C / D（可参考建议，以你的判断为准）。批注选填。
4. 不能用：把「评审结论」改成 **驳回**，在「评审批注」写一句原因。
5. 等下一次 intake（定时或手动 `repository_dispatch`）。大约 1–2 分钟后：状态变成「已通过 / 已驳回」，回礼多一行评审结果；通过的原子进入下一版 skill，驳回的不再重收。

人员字段「评审人」有值就用名字；没有则记 `maintainer`。

## 不要做的事

- 不要手改 `pending.jsonl` / `approved.jsonl` 来定级。
- 不要改 `knowledge/04-atoms/growth-layers.approved.jsonl`。
- 不要因为「这是平台技巧」就驳回；技巧只打风险标签，仍按内容好坏决定。
- 不要把「状态」当成评审开关。发布看「评审结论」。撤回才把「状态」改成「撤销」。

## 宽松收录

内测默认照单全收进待审。含手机号/证件/密钥的投稿：宽松会脱敏后待审；严格会停在「需人工」。打开那一行清掉隐私再等下次拉取。

互相打架的判断句会写进 `lifecycle.contradicts`，不会自动判谁对；两条都可以过或驳。

## 停止线

出现未处理的隐私投诉，先停 Action（workflow 里 disable），清数据后再开。不要「先入库以后再洗」。
