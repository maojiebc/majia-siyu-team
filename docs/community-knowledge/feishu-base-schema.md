# 飞书多维表格字段说明（v1.5.1 共创管线）

目标：一张表收投稿，一张表收印证。每日 GitHub Action 拉取后写入 `knowledge/05-community/`，下次构建自动带上。

维护者只需在飞书里建好表和表单；字段名必须与下表一致，否则拉取对不上。公开表单 15 个字段 + 系统回写列。`我也遇到过` 是回链，不进表单。

系统列（表单不要展示，Action 回写）：

| 字段名 | 飞书类型 | 取值 |

## 表二：`印证`

驱动「≥2 家不同公司独立确认 → 自动升 C」。

|---|---|---|---|

| 印证的原子ID | 文本 | 表单侧必填 | 印证人从案例卡/回礼里复制 `ka_…` 贴上 |
| 印证人公司 | 文本 | 是 | 入库前哈希，必须和原投稿不是同一家 |
| 印证时间 | 日期 | 是 | 印证人确认的日期 |
| 对外显示名 | 文本 | 否 | 公开署名，按设计镜像到公开 Base，不做哈希。空则按「匿名同行」 |

环境变量：`LARK_TABLE_CONFIRMATIONS`（已是 `tblclv6LhLPIKQP4`）。解析顺序：关联 `record_id` → `印证的原子ID`（去空白、小写，有无 `ka_` 都行）→ 关联展示文本。对不上的记入 `confirmations_unresolved`，不中断。

同一判断句被另一家公司再交一版（去重 Jaccard ≥ 0.8）也算印证，不要求只走这张表。

## 飞书 CellValue 形态

拉记录时按实际 API 形态解析，不要假设只有一种：

| 字段类型 | 常见返回 | 也要认 |
|---|---|---|
| 单选 | `["餐饮·正餐"]` | 纯字符串；旧值 `["餐饮"]` |
| 多选 | `["企业微信","小程序会员"]` | 纯字符串或带 `text` 的片段 |
| 日期 | `"2026-09-03T00:00:00.000+08:00"` | 毫秒时间戳（按 `Asia/Shanghai` 取日历日） |
| 关联 | 空=`null`；有值=`[{"id":"rec…"}]` | `record_id` / `record_ids` / `text` |
| 文本 / 多行文本 | 纯字符串 | `[{"text":"…","type":"text"}]` 片段 |

## 表单字段 → 原子字段

| 表单 | KnowledgeAtomV2 |
|---|---|
| 一件有效的事（或没用的事） | `statement` |
| 这条属于 | `type`（平台技巧→`platform_workaround`，文案钩子→`hook_pattern`，排版→`layout_pattern`，发送时机→`timing`，数字基线→`benchmark`，反例翻车→`anti-pattern`，厂商体验→`vendor_experience`，规则变化→`rule_change`，方法→`method`） |
| 业态 / 细分 | `scope.industry` / `scope.subindustry`。前缀 `餐饮·`、`咖啡茶饮`、`烘焙甜品`→`catering`；前缀 `零售·`→`retail`；`其他`→`other`。旧值「餐饮」「零售」仍认。细分有则接到标签后 |
| 经营模式 | `scope.business_model`（直营→direct，加盟→franchise，混合→mixed） |
| 门店数 | `scope.scale_band`（旧值 `300+` 记为 `any`） |
| 分公司层 | `scope.org_layers`（有→regional，没有→none，不清楚→any） |
| 你的位置 | `source.contributor_role`（总部→hq，分公司或区域→regional，加盟商→franchisee，门店→store，服务商或顾问→vendor_or_consultant；缺省 unknown） |
| 主要私域载体 | `scope.channels`（企业微信→wecom，个人微信→personal_wechat，微信社群→wechat_group，小程序会员→miniprogram_member，公众号→official_account，抖音快手私信→douyin_kuaishou_dm，小红书→xiaohongshu，其他→other） |
| 数字/证据 | `applicability.metrics[]`；空则写「指标不适用」 |
| 发现时间 | `source.observed_at`、`lifecycle.valid_from` |
| 现在还有效吗=已失效 | `valid_until`=发现当日（立即过期，仍留档） |
| 平台技巧 / 规则变化 | 180 天窗：`是`→创建时间（缺则今天）+180 天；`不确定`→发现时间+180 天，且不早于今天+30 天；`已失效`→发现当日。印证到达则 `valid_until` 延到印证日+180 天。`quality.platform_rule_risk` 由关键词扫描标注，不拒收 |
| 公司/品牌 | `quality.confirmations[].company_hash` |
| 联系方式 | 不入库；仅用来匹配 `SIYU_MAINTAINER_IDS` |
| 对外显示名 | `source.contributor_display_name`；印证写入 `quality.confirmations[].display_name`。空=匿名同行。公开字段，不哈希；含手机号/邮箱时宽松改匿名并备注，严格需人工 |

原子 `id` = `sha256(归一化判断句 + company_hash)` 的前 16 位，前缀 `ka_`。

## 哈希规则

- 环境变量 `SIYU_HASH_SALT`：仓库级盐，至少 16 字符，不入库。
- 公司名先去括号地区、法律/业态后缀（如有限公司、集团、（上海）、上海分公司），再去空白标点并转小写，再算 `sha256(盐 + 换行 + 归一化名称)`。
- 贡献者哈希用「联系方式」；没有联系方式时用记录 ID。原文都不进 JSONL。
- `印证.关联提交` 先绑 `record_id`/`id`（`rec_…`）；表单侧请填 `印证的原子ID`；都没有才用关联展示文本。

## 自动信任

- 单源 → 证据等级 `D`，写入 `inbox.jsonl`，状态 `已收录D`。
- ≥2 个不同 `company_hash` **且** ≥2 个不同 `contributor_hash` → `C`，写入 `confirmed.jsonl`，状态 `已晋级C`。自评（印证的公司或贡献者与原投稿相同）不计；同公司第二条只算一家。
- 联系方式命中 `SIYU_MAINTAINER_IDS` → `A`，写入 `maintainer.jsonl`。A/B 不能由管线自动生成（B 只能维护者手改 JSONL）；下次运行 A/B 保持原等级。
- 判断句、证据或对外显示名里扫到手机号、身份证、邮箱、密钥、门店编号：严格 → 状态 `需人工`；宽松 → 判断句/证据就地脱敏、显示名改「匿名同行」并备注。原文 PII 不入库。
- 平台技巧只打风险标签，仍按 D/C 入库。
